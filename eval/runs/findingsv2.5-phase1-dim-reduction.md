## Configuration shipped

```yaml
clustering:
  min_cluster_size: 5
  min_samples: 5                  # reverted 10 → 5; Tier 2's 10 over-tightened
  selection_epsilon: 0.0
  selection_method: leaf          # was eom; "many fine-grained roles" goal
  distance_metric: cosine

  dimensionality_reduction:
    method: umap
    n_components: 15
    umap:
      n_neighbors: 10
      min_dist: 0.0
      metric: cosine
      random_state: 42
```

When `dimensionality_reduction.method != "none"`, the HDBSCAN call:
- switches `metric` from `cosine` → `euclidean` (the reduced space is L2 by construction)
- switches `algorithm` from `generic` → `best` (KD-tree available in low-D)

`cluster_selection_method` is now wired through to HDBSCAN (it was not in the constructor before this PR).

## Known issues to address in Phase 2 / follow-ups

### Exact-name duplicates (~5)

The LLM labeler returns identical strings for distinct cluster centroids. Confirmed reproducible across runs:

```
'AI Software Engineer'                  ×3
'Data Scientist'                        ×2
'Senior Cloud Infrastructure Engineer'  ×2
'Senior Data Engineer'                  ×2
'Site Reliability Engineer'             ×2
```

Investigation on the previous run's `Senior Data Engineer` pair showed cosine distance 0.145 between centroids with meaningfully different tool profiles (one generic, one Snowflake/dbt-specialised) — i.e. the clusters are *legitimately distinct sub-roles*, the labeler just picked the same name. Fix in Phase 2 is **labeler hardening** (synthesize the role name from cluster fingerprint instead of echoing `representative_titles[0]`), not `cluster_selection_epsilon` tuning. Sub-issue filed under #327.

### Stale orphan row (1)

`Senior Civil Drainage Engineer` (`computed_at = 2026-04-16`) has only 1 posting still pointing at it but `cleanup_orphan_canonical_roles` doesn't catch it. Likely the cleanup predicate checks `posting_count = 0` instead of querying the JOIN count directly. Sub-issue filed under #327.

### Generic catch-all clusters

`Software Engineer` (#182, 6 posts) is generic enough that it should probably merge into a more specific software-engineer cluster. Suggests either:
- `min_cluster_size: 5` is too permissive (try 8 in Phase 2)
- The labeler should refuse to use generic 2-word titles when more specific options exist

### Smoke test threshold mismatch

The smoke test's hardcoded `noise_fraction < 20%` threshold fails (we hit 43.3% in the smoke's broader denominator, 31.1% in the findings JSON's clustering-input-only denominator). Phase 5 of #327 plans to update this threshold to 30%; for now the smoke's noise check is informational, not gating.

### Employer-specific labels leak into canonical names

E.g., `Mobile Application Developer (iOS / Android) (2-4 years of exp) - USC and GC's` is one company's exact job title surfacing as a canonical role name. The labeler uses `representative_titles[0]` rather than synthesizing a clean role label. Pre-existing behavior, exposed here by the long tail of small clusters. Worth a follow-up on the labeler's dedup/synthesis logic.
